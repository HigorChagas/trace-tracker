# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Solo Python developers, debugging alone. They hit an error, copy the traceback, and want a fast, trustworthy explanation without leaving their own machine or pasting code into a third-party chat tool. Not a team/shared-triage tool today.

## Product Purpose

Trace Tracker turns a raw Python stack trace into a clear explanation: what the error is, its probable cause, and how to fix it with example code. It exists to shortcut the "google the exception, skim three Stack Overflow answers" loop. Success is a developer getting an accurate, actionable explanation faster than manual searching, plus a personal history they can revisit.

## Positioning

Unlike pasting an error into a general-purpose AI chat, Trace Tracker only analyzes errors it recognizes against a curated known-error database (seeded from Python's built-in exception/warning hierarchy) before generating an explanation. This lookup-then-explain pipeline is a deliberate accuracy guardrail, not an MVP shortcut: it scopes the AI to errors the product can vouch for, rather than free-form text that risks a hallucinated diagnosis. Errors outside the known-error set are explicitly rejected rather than guessed at.

## Operating Context

- Developer pastes or sends a stack trace (via web UI or the API directly).
- Backend takes the last line of the trace, matches it case-insensitively against `known_errors` (name + summary), and only then calls the AI for the full explanation.
- Explanation is generated by a local Ollama model by default (or any OpenAI-compatible endpoint as a fallback), then saved to that user's history for later lookup.
- User can browse, open, and delete past analyses (paginated history).

## Capabilities and Constraints

- Auth: JWT-based register/login; all analysis and history endpoints require a valid token.
- Analysis is Python-only today (`language` is stored per entry, hinting at future multi-language support, but no other language is seeded or supported now).
- Only errors present in the `known_errors` table are analyzed; unrecognized errors return a 404 rather than a best-effort AI guess.
- History entries are user-scoped; a user cannot read or delete another user's entries (403 enforced).
- Storage is SQLite via SQLAlchemy async — a single-instance, self-hosted footprint, consistent with the personal-tool positioning above.

## Brand Commitments

- Product name: **Trace Tracker**.
- Local-first AI is a durable commitment: Ollama is the default, recommended AI backend specifically for privacy (stack traces can contain sensitive code/data) and zero inference cost, not merely today's default configuration. Any OpenAI-compatible API remains an explicit opt-in alternative, not the primary path.

## Evidence on Hand

- `seed.py` — the known-error dataset: ~50 built-in Python exception and warning types with plain-language summaries, tagged `language: "Python"`.
- `README.md` — setup instructions, endpoint table, and a usage example, current and authoritative for API shape.
- No customer testimonials, case studies, usage metrics, or pricing exist; future work must not fabricate them.

## Product Principles

1. Trust the diagnosis: never let the AI explain an error the product hasn't verified against the known-error set.
2. Keep it personal and local: default to on-device/self-hosted AI inference; treat cloud AI as an opt-in, not the default story.
3. Python-first, not Python-only-forever: the data model anticipates other languages, but no other language should be implied as supported until seeded.
4. History is a personal debugging log, not a shared team record — scope every read/delete strictly to its owner.
